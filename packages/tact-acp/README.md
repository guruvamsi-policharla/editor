# tact-acp

An ACP agent for [tact](https://github.com/clabby/tact) ("A terminal interface for Nanocodex"), so the editor's chat panel can drive it (tact is the chat's only harness). tact has no ACP mode and no headless session mode (checked again at tact `main` @ `fd47ff6`, Oct 12, 2026: `tact run <PROMPT>` is headless but runs one prompt as one turn and prints JSONL, with no way to continue or resume a session, and no approvals), so this adapter:

- runs tact's terminal UI in a pty nobody sees (`script(1)`), one tact process per ACP session, because the web API only runs while the UI does and its event stream follows the UI's active session;
- is that pty's terminal: tact asks its terminal what it supports when it starts (kitty keyboard `CSI ? u`, kitty graphics `APC G … a=q`, cell size `CSI 16t`, device status `CSI 5n`, then DA1 `CSI c`) and waits for the answers. Unanswered, that cost 2 s per start on Linux and hung past the 30 s start timeout on macOS ("tact started, but its web server didn't come up within 30 s"). The adapter answers like a plain VT220-class terminal (DA1 without sixel, so tact uses no kitty protocol), through `script`'s stdin (`src/terminal.ts`, `src/process.ts`): on Linux a FIFO only the adapter writes to; on macOS a real pipe, because BSD `script` refuses a socket stdin and a Node pipe and a macOS FIFO are both sockets ("tcgetattr/ioctl: Operation not supported on socket"), so bash execs `script` with a process substitution `cat` feeds from the adapter's stdin. The pty is 160×48 (`stty`), and tact's output, kept for error messages, has every escape sequence removed;
- ends tact when the adapter goes: `script` reads EOF on the FIFO, and a watcher in the pty's shell ends tact once the adapter's pid is gone (macOS `script` ignores EOF), so a killed adapter never leaves a tact behind;
- finds the instance through tact's registry (`$TACT_HOME/web/instances/<pid>.json`) and machine token (`$TACT_HOME/web/token`);
- bridges ACP to tact's local web API (protocol 10, tact `docs/web.md`, on tact's main branch after v0.8.3).

| ACP | tact web API |
|---|---|
| `session/new` | start tact; its first session is the ACP session (same id) |
| `session/load` / `session/resume` | start tact with `--resume <id>`; load replays the snapshot's entries |
| `session/prompt` | `set_draft`, then `submit` with the draft's revision; entry upserts stream back until the turn's `turn_completed` / `interrupted` / `error`. One turn at a time per chat, each with its own state: a message sent while the last one is still running or ending (Stop and send again, an earlier message edited and sent again) stops that one, waits for it, then goes. A `set_draft` tact's terminal didn't answer in time (HTTP 503) is sent once more; any failure ends only that message |
| `session/cancel` | `interrupt`; a Stop that comes before tact started the turn (`nothing_running`) interrupts it as soon as it starts, or the message isn't sent at all. A turn tact hasn't ended 10 s after Stop ends as cancelled anyway |
| `session/set_config_option` | `set_model` (before the first message), `set_effort`, `set_reasoning_mode`, `set_speed`; `settings` events → `config_option_update` |
| model / reasoning mode change | tact starts a new session for it (a new id) and closes the old one: the adapter waits for the new session's snapshot and follows it, the ACP session keeps its id (`$TACT_HOME/editor-sessions.json` maps it to tact's session, for `--resume`). If tact can't start it (a refused Claude key), it keeps the old session and says why only in its terminal: the adapter reads that notification and fails the change with it |
| config options | from tact's `models` catalog, per model (`src/mapping.ts`): the model (catalog order, provider as description; only the current one after the first message), thinking (the catalog's efforts; only the current one once a model with `effort_fixed_after_start` has started), reasoning mode (only when the model lists more than one; only the current one after the first message), speed (only the tiers in the catalog's `speeds` the model runs at itself, per `effective_speeds`; no option when that's one). A value an option doesn't offer is refused with what it offers. After a model change the effort and speed are set again on tact's new session (it starts from tact's defaults), the speed as the tier the new model runs; at start and when the catalog changes too (`normalize`) |
| `$TACT_HOME/config.toml` (or `TACT_CONFIG`) changes | `reload_config`, then the `models` query again: a key added while tact runs brings its models to the picker (`config_option_update`); a model the catalog lacks is looked up again before `set_model` |
| a refused request | the ACP error is tact's message with the request, HTTP status and code (`refused the request: unknown session (set_draft: HTTP 404 unknown_session)`), never a bare "Internal error" |
| message / thought chunks | `assistant` / `reasoning` entries, diffed (tact re-sends an entry whole on every revision) |
| tool calls | `tool` entries (`apply_patch` → edit, titled with tact's `+/−` stats, its files as absolute locations; `exec_command` → execute, with its output tail), plus the entry detail for output. A Code Mode `exec` cell that becomes the tool it ran (a later revision of the same entry) updates the call's kind and name |
| usage, title | `context` events, the session summary's title |
| auth required | tact exits at start with "no ChatGPT credentials …"; or the first request is refused (HTTP 401, an expired login): the chat then offers Sign in (`tact auth login`) |

tact never asks for permission (Nanocodex runs with approval "never" and full access), so there are no permission requests and no approvals picker: the pickers are only the ones tact has, as the catalog gives them for the session's model. The adapter never calls the client's `fs/*` or `terminal/*`, and the editor advertises neither: tact edits files and runs commands itself, and the editor's review shows its edits with Keep/Undo.

What upstream would make this simpler: a `tact acp` subcommand (stdio ACP, headless, one process for many sessions), or a headless `tact serve` that runs the web API without the terminal UI.

Install: the web API is on tact's main branch after v0.8.3, so a pre-release build: `curl -fsSL https://tact.clab.by/install.sh | TACT_CHANNEL=pre-release sh` (or `tact update <commit>`), then `tact auth login`. The chat offers both when tact is missing or signed out.

Env: `TACT_BIN` (the tact binary; default `tact`), plus tact's own (`TACT_HOME`, `TACT_CONFIG`, `CODEX_HOME`, `OPENAI_API_KEY`, `TACT_API_BASE_URL`, `TACT_TRANSPORT`; set them for the chat with `agentChat.harnesses.tact.env`). Bundled into agent-chat as `dist/adapters/tact-acp.js` and run with the editor's Node.

Tests (`npm test`): the entry mapping, the terminal (escape sequences stripped, queries answered across chunks), and the agent end to end (two chats at once, Stop and send again, an edited message sent while a turn runs, a busy terminal's 503) against a fake tact (`test/fixtures/fake-tact.mjs`, a small server speaking the same API) in a real pty. The fake asks the start-up queries and, like tact on macOS, waits for the DA1 answer with no timeout, so an adapter that doesn't answer fails the start test (CI runs it on Linux and macOS). On Linux the macOS launch also runs through a shim `script` that refuses a socket stdin like BSD's (`test/fixtures/bsd-script`). `packages/acp-client/test/tact.test.ts` runs the bundled adapter over ACP stdio, as the editor does.

`test/real-tact.test.ts` runs the adapter on a real tact (`TACT_REAL_BIN=/path/to/tact npx vitest run test/real-tact.test.ts`) against `test/fixtures/model-mock.mjs`, a local mock of the Anthropic Messages and OpenAI Responses APIs: a Claude model picked on a new chat and sent at once, a refused Claude key, a key added while tact runs, and each model's pickers (speed tiers, effort fixed after the first turn on Claude) from the real catalog. `test/fixtures/models-98ffe05.json` is the catalog of tact dev-98ffe05 with OpenAI, Claude and Glasswing keys, used by the unit tests here and in agent-chat. Checking with the real tact but no account: point it at a local mock of the Responses API (`agentChat.harnesses.tact.env`: `OPENAI_API_KEY` any value, `TACT_API_BASE_URL=http://127.0.0.1:<port>/v1`, `TACT_TRANSPORT=https`). tact runs in Code Mode: the model gets one custom tool, `exec` (JavaScript calling `tools.apply_patch(…)`, `tools.exec_command(…)`), and `wait`.
